# 数据质量检查清单

reviewer_data 收到分析师产出后**逐项过这张表**。每项写在审查报告里("通过/未通过/不适用")。

## A. 数据加载与速看(对照 data_analysis_workflow Step 1)

- [ ] 脚本里有打印 `df.shape` 的输出
- [ ] 脚本里有打印 `df.dtypes` 的输出
- [ ] 脚本里有打印 `df.isna().sum()` 的输出
- [ ] 加载的字段类型与业务预期匹配(date 是 datetime 不是 object)
- [ ] 时间字段解析失败没被默默忽略(`errors='coerce'` 后有 NaT 检查)

## B. 清洗

- [ ] 缺失值处理策略**明确写注释**说为什么这么做
- [ ] 关键字段(user_id / order_id 等)缺失被丢弃而不是填默认值
- [ ] 丢弃行时有打印"丢了多少行"
- [ ] 异常值处理有阈值依据(业务上限/分布观察),不是凭感觉
- [ ] 去重处理是基于业务唯一键(order_id 而不是全行去重)

## C. 统计正确性

### 分母

- [ ] 比率类指标(转化率/留存率)的**分母去重**了(`.nunique()` 而不是 `.count()`)
- [ ] 多个数据源 join 时验证了 join key 在右表唯一(否则会膨胀)
- [ ] 时间窗口是闭区间还是半开区间明确(date < end vs date <= end 差一天)

### 分组

- [ ] 分组维度对齐业务边界(web/app 不混算)
- [ ] groupby 后的聚合用对函数(`sum` / `mean` / `nunique` 不混淆)
- [ ] 时间分组按业务时区(不要 UTC 当本地时间)

### 同环比

- [ ] pct_change 的 periods 参数和文字描述一致
- [ ] 跨年/月边界正确处理(2 月 28/29 天)
- [ ] 涨幅是百分点还是百分比说清楚(从 30% 涨到 36% 是 +6pp 还是 +20%?)

## D. 口径一致性

- [ ] 分析脚本里的指标定义**逐字符**对照 research_data 给的口径
- [ ] 多处用同一指标时计算逻辑一致(没有这里 distinct count 那里 count 的)
- [ ] 业务术语首次出现时定义清楚("活跃" = 哪个口径下的活跃)

## E. 结论可追溯

- [ ] 报告里每个数字能在脚本输出里找到
- [ ] "显著"、"明显"等词后必跟具体数字
- [ ] 因果性主张("X 导致 Y")必须有对照组或实验数据
- [ ] 推论范围不超过数据覆盖期(用 3 个月数据下"全年"结论 → ⚠️)

## F. 常见陷阱

- [ ] **辛普森悖论**:总体趋势和分组趋势相反时是否做了说明
- [ ] **幸存者偏差**:用现有用户分析"用户行为"是否忽略流失用户
- [ ] **季节性**:看同期增长有没有去年同期数据对照
- [ ] **小样本**:n < 30 的"结论"必须降级为"初步观察"
- [ ] **百分比基数**:"增长 200%" 基数是 1 还是 1000 ?

## G. 工程质量(轻量,不强求)

- [ ] 脚本能独立跑通(不依赖外部状态、临时变量)
- [ ] 图表保存路径在 `output/`,不污染源数据目录
- [ ] 脚本运行时间合理(< 1 分钟,长耗时要切分或采样)

## 审查输出模板

按以下格式写审查结论:

```
## 审查结论
✅ 通过 / ⚠️ 需修改 / ❌ 拒绝

## 检查清单结果

A. 数据加载: ✅ 全过 / ⚠️ 缺 isna 检查
B. 清洗: ⚠️ 缺失值策略不明
C. 统计: ❌ 转化率分母没去重
D. 口径: ✅
E. 可追溯: ⚠️ 报告说"显著上涨"没数字
F. 陷阱: ✅
G. 工程: ✅

## 必修问题(致命)

1. [scripts/analysis.py:42] 转化率分母 `df.user_id.count()` 应该用 `nunique()`,
   否则同一用户多次访问被算多次。当前数据下转化率被低估约 18%(估计)

## 建议改进(重要)

1. [scripts/analysis.py:55] amount 缺失值用 `fillna(0)` 没说明依据,
   建议加注释"订单生成失败时金额为空,业务上视为 0",或调整为丢弃这些行。

## 通过项

- 数据加载阶段做了完整速看,可信
- 时间字段处理正确
- 图表数字配比较基线,可读性好

## 总结

主要问题在统计正确性(C),修完后重审。整体分析方法论扎实,业务洞察明确。
```

## 不要做的

- ❌ 评价分析师水平 / 风格(就事论事)
- ❌ 苛求完美主义(差 1pp 不算错)
- ❌ 改业务口径(那是 research_data 的活)
- ❌ 提议重写架构 / 换技术栈(分析师产出能用就行,不优化代码风格)
